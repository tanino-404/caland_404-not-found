# 系統的デバッグ

## 概要

**原則：** 修正の前に必ず根本原因を特定する。症状だけを直すのは失敗である。

**手続きの文言を破ることは、デバッグの精神を破ることである。**

## 鉄則

```
根本原因の調査を終えるまで、修正しない
```

フェーズ 1 を終えていないなら、修正案を出してはならない。

## 使うとき

技術的な問題なら使う。
- テスト失敗
- 本番のバグ
- 想定外の動き
- 性能の問題
- ビルド失敗
- 結合の問題

**特に次のときは必須：**
- 時間がない（緊急ほど当て推量が誘われる）
- 「ちょっと直せば終わる」に見える
- すでに何度か直している
- 前回の修正が効かなかった
- 問題を十分理解していない

**飛ばさない：**
- 単純に見える（単純なバグにも根本原因がある）
- 急いでいる（急ぎは手戻りを保証する）
- 今すぐ直せと言われている（系統的な方が、もがくより速い）

## 4つのフェーズ

次のフェーズへ進む前に、そのフェーズを完了する。

### フェーズ 1: 根本原因の調査

**いかなる修正の前にも：**

1. **エラーメッセージを丁寧に読む**
   - エラーや警告を飛ばさない
   - 解決そのものが書いてあることが多い
   - スタックトレースは最後まで読む
   - 行番号、ファイルパス、エラーコードを控える

2. **再現を安定させる**
   - 確実に起こせるか
   - 手順は何か
   - 毎回起きるか
   - 再現できない → 推測せず、データを増やす

3. **最近の変更を見る**
   - 何が原因になり得る変更か
   - 差分、直近のコミット（参照のみ。git 操作は人間の仕事）
   - 新しい依存、設定変更
   - 環境の差

4. **複数コンポーネントのときは証拠を集める**

   **システムが複数段あるとき（CI → ビルド → 署名、API → サービス → DB）：**

   **修正案の前に、診断用の記録を足す：**
   ```
   コンポーネント境界ごとに：
     - 入ってくるデータを記録する
     - 出ていくデータを記録する
     - 環境／設定の伝播を確認する
     - 各層の状態を見る

   1回動かして、どこで壊れるかの証拠を取る
   それから証拠を分析して失敗しているコンポーネントを特定する
   それからそのコンポーネントだけを調べる
   ```

   **これで分かること：** どの層が失敗しているか（例: secrets → workflow は成功、workflow → build は失敗）

5. **データの流れを辿る**

   **エラーがコールスタックの深いところにあるとき：**

   同じディレクトリの `root-cause-tracing.md` に、呼び出しを遡る技法の全文がある。

   **短い版：**
   - 悪い値はどこで生まれたか
   - 誰が悪い値を渡したか
   - 発生源まで遡る
   - 症状ではなく発生源を直す

### フェーズ 2: パターン分析

**直す前にパターンを見つける：**

1. **動いている例を探す**
   - 同じコードベースで似ていて動いている箇所
   - 壊れているものに近い、動いているものは何か

2. **参照実装と照合する**
   - パターンを実装するなら、参照実装を最後まで読む
   - 斜め読みしない。毎行読む
   - 適用する前にパターンを理解する

3. **差を列挙する**
   - 動いているものと壊れているものの差は何か
   - 小さくても全部書く
   - 「それは関係ない」と決めない

4. **依存を理解する**
   - 他に必要なコンポーネントは何か
   - 設定、環境は何か
   - どんな前提を置いているか

### フェーズ 3: 仮説と検証

**科学的方法：**

1. **仮説は1つ**
   - 「根本原因は X だ。理由は Y」と明確に書く
   - 曖昧にしない

2. **最小で試す**
   - 仮説を試す変更は可能な限り小さく
   - 変数は一度に1つ
   - 同時に複数箇所を直さない

3. **続けてよいか確認する**
   - 効いた → フェーズ 4
   - 効かない → 新しい仮説を立てる
   - その上に修正を積み重ねない

4. **分からないとき**
   - 「X が分からない」と言う
   - 知っているふりをしない
   - 人間に聞く
   - 調べる

### フェーズ 4: 実装

**症状ではなく根本原因を直す：**

1. **失敗する確認を先に用意する**
   - いちばん単純な再現
   - 本プロジェクトではテストコードは書かない。アプリを起動し、Cursor 内蔵ブラウザで再現する
   - 直す前に必須

2. **修正は1つ**
   - 特定した根本原因だけを扱う
   - 一度に1変更
   - 「ついで」の改善を入れない
   - リファクタを同梱しない

3. **修正を確認する**
   - 再現手順で直っているか
   - 他の画面・操作が壊れていないか
   - 問題が実際に解消したか

4. **効かないとき**
   - 止まる
   - 何回直したか数える
   - 3回未満：フェーズ 1 に戻り、新しい情報で再分析する
   - **3回以上：止まって、構成そのものを疑う（下記 5）**
   - 構成の議論なしに 4 回目の修正をしない

5. **3回以上失敗したら構成を疑う**

   **構成の問題を示すパターン：**
   - 直すたびに、別の場所の共有状態／結合／問題が出る
   - 直すのに「大規模リファクタ」が要る
   - 直すたびに別の症状が生まれる

   **止まって、土台を問う：**
   - このパターンはそもそも健全か
   - 惰性で続けていないか
   - 症状を直し続けるより、構成を組み替えるべきか

   **これ以上直す前に、人間と話す**

   これは仮説の失敗ではなく、構成が間違っている。

## 危険信号 — 止まって手続きに戻る

次のように考えたら：
- 「今は応急、調査は後」
- 「X を変えてみて効くか見る」
- 「複数変えてから確認する」
- 「確認は手でやるからテストは飛ばす」（本プロジェクトではアプリ起動確認は必須）
- 「たぶん X だ、直そう」
- 「よく分からないがこれで動くかもしれない」
- 「パターンは X だが、自分流にアレンジする」
- 「主な問題はこれです」と、調査なしに修正リストを出す
- データの流れを辿る前に解を出す
- **「もう1回だけ直す」（すでに 2 回以上試している）**
- **直すたびに別の場所の新しい問題が出る**

**どれも意味は同じ：止まる。フェーズ 1 に戻る。**

**3回以上失敗したら：** 構成を疑う（フェーズ 4 の 5）

## 人間からの「やり方が違う」合図

**次の差し戻しに注意する：**
- 「それは起きていないのでは」 — 確認せずに仮定した
- 「それで分かるか？」 — 証拠を取る計測を足すべきだった
- 「当て推量をやめろ」 — 理解せずに修正を出している
- 「根本から考えろ」 — 症状ではなく土台を疑う
- 「行き詰まった？」（苛立ち） — やり方が効いていない

**これを見たら：** 止まる。フェーズ 1 に戻る。

## よくある正当化

| 言い訳 | 実際 |
|--------|---------|
| 「単純だから手続きは不要」 | 単純な問題にも根本原因がある。単純なバグほど手続きは速い。 |
| 「緊急で手続きの暇がない」 | 当て推量でもがくより、系統的デバッグの方が速い。 |
| 「まずこれを試して、あとで調べる」 | 最初の修正が型になる。最初から正しくやる。 |
| 「直ってから確認を書く」 | 確認なしの修正は定着しない。直す前の再現が証明になる。 |
| 「まとめて直す方が速い」 | 何が効いたか切り分けられない。新しいバグの原因になる。 |
| 「参照が長いからパターンをアレンジする」 | 中途半端な理解はバグを保証する。最後まで読む。 |
| 「問題が見えた、直す」 | 症状が見えることと、根本原因を理解することは別である。 |
| 「もう1回だけ」（2回以上失敗したあと） | 3回以上の失敗は構成の問題。また直さず、パターンを疑う。 |

## 早見表

| フェーズ | 主な作業 | 完了条件 |
|-------|---------------|------------------|
| **1. 根本原因** | エラーを読む、再現する、変更を見る、証拠を集める | 何が・なぜ が分かる |
| **2. パターン** | 動いている例を探し、比較する | 差が特定できる |
| **3. 仮説** | 仮説を立て、最小で試す | 確認できた、または新しい仮説 |
| **4. 実装** | 再現確認、修正、検証 | バグが消え、確認が通る |

## 「根本原因なし」と出たとき

系統的な調査の結果、環境依存・タイミング・外部要因だと分かった場合：

1. 手続きは完了している
2. 何を調べたかを記録する
3. 適切な扱いを実装する（再試行、タイムアウト、エラー表示）。フォールバックでエラーを飲み込まない
4. 今後の調査用にログを足す

**ただし：** 「根本原因なし」の 95% は調査不足である。

## 補助技法

同じディレクトリにある。系統的デバッグの一部である。

- **`root-cause-tracing.md`** - コールスタックを遡り、最初の引き金を見つける
- **`defense-in-depth.md`** - 根本原因を特定したあと、複数層で検証を足す
- **`condition-based-waiting.md`** - 適当な待ち時間を、条件ポーリングに置き換える
