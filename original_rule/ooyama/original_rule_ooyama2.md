## 1. 合格ライン（動画審査）

主催の基準はチャレンジ度・ギーク度・ワクワク感。画面を開いた人が、説明を聞かなくても「地形から予定の村ができる」と分かること。

監査はアプリを起動して行う。次をすべて満たすまで、その作業は完了にしない。

1. **動作。** `cd src && npx tsc --noEmit -p tsconfig.app.json && npm run lint && npm run build` が通る。家計簿サーバーを触った作業では、仮想環境を有効にして `cd server && source .venv/bin/activate && python -m unittest discover -s tests -v` も通す。
2. **動画と同じ動線が、サンプルデータだけで最後まで通る。**
5. **本機。** 録画するシーンがラップトップ上でカクつかないこと。Console のエラーは、動画の途中で画面が壊れるものを直す。
6. **初見。** 次に押すものが画面から分かること。月を送る、日に寄る、年へ戻る、家計簿を開く、が迷わない。

世界観はマイクラ風の地形と町のままにする。見た目を一般的な企業サイトの UI に寄せて、村の驚きを弱める変更はしない。

## 2. 進め方

- 親エージェント（Grok4.7）が、分解・優先順位・監査・共有ファイルの編集を持つ。実装は、ファイルの範囲を切って部下に渡してよい。
- 部下のモデルは、ホストがその場で指定したものにする。指定が無いときはそのセッションの既定でよい。モデルを Opus と Sonnet だけに固定しない。2026-10-16 にその固定で作業が止まり、ホストは Grok を部下にしてよいと指示している。
- 部下へは、触ってよいファイルと「§1 の動線を壊さない」ことを渡す。仕様が割れたら部下が決めず、親がホストに聞く。
- 共有ファイルは親だけが編集する。対象は `package.json`、lock ファイル、`vite.config.ts`、エントリ（`main.tsx` / `index.html`）、全体スタイル、`README.md`。
- ライブラリを足すときは、名前と理由を人間に伝えてからにする。部下が個別に `npm install` しない。
- ホストが「次にやる機能」を指定するまでは、別機能に着手しない。1作業は、動画の1カットに対応する大きさにする。
- 締切に収まらない見込みの機能は削る。削った内容は報告に書く。
- 既存の `docs/architecture/architecture.md` を、作業のついでにひっくり返さない。公開 URL を足すなど構成を変えるときは、人間が決めたあと architecture を更新する。

## 3. 実行環境

- 開発と録画の確認は、このラップトップで行う。ディスクリート GPU は無い前提で、§1 の動線が滑らかに動くこと。
- 3D（three.js）は作品の本体である。谷野ルールの「重い 3D を行わない」は使わない。パーティクル、影、反射を足すときは、本機で録画できる負荷に収める。収まらなければ足さない。
- 公開 URL へのデプロイは、人間が決めるまでしない。先に、手元で動画と同じ操作が再現できること。
- 秘密情報は `.env` で受け取る。サンプルは `secret/.env.template`。コードと `config/` に書かない。
- キーをフロントに置かない。Vite の `VITE_` 付き環境変数はビルド結果に入り、ブラウザから見える。キーに `VITE_` を付けない。
- 企業の API・SDK は応募の必須ではない。使うと決めたときだけ、キーがフロントに出ない構成にし、ProtoPedia の「API・素材等」へ登録する旨を人間に伝える。

## 4. コード

角田ルールの書き方を、評価軸だけオンラインリーグに合わせて残す。

- 着手前に、現状、ゴール、変更箇所、手順を短く述べる。変更は必要なファイルだけにする。
- 新たに書く箇所は、`docs/architecture/architecture.md` の技術スタックと、その公式ドキュメントに合わせる。スキルと公式ドキュメントが食い違うときは公式ドキュメントを優先する。
- シンプルで読めるコードにする。過度な抽象化をしない。重複は1か所にまとめる。
- エラーを飲み込まない。別の値を返すフォールバックを書かない。エラー情報を出して止める。
- 見た目は §1 に従う。配置、余白、画面幅が変わっても操作できることは守る。奇抜さは、村と地形の驚きを強める範囲で使う。
- 作業後にリンターを確認し、エラーを解消する。
- テストコードは書かない。確認は起動と、§1 の動線を Cursor のブラウザで操作すること。谷野ルールのカバレッジ 90% と、テストを先に書くスキルは使わない。

### React / TypeScript（このアプリの画面）

- コンポーネントは `export const ComponentName = () => {}`。1コンポーネントは1関心事。巨大なら子や Hook に分ける。最初から細かく分けすぎない。
- `any` は使わない。不明なら `unknown` と型ガード。Props、引数、戻り値には `interface` または `type` を書く。
- boolean の props が3つ以上になったら、合成に直す。
- データの取り方と再レンダリングは、直列の待ちすぎ、不要な重い import、無駄な再描画を避ける。

### Python（家計簿サーバー）

画面を触らない作業では、この節は使わない。

- PEP 8。インデントはスペース 4。関数と変数は `snake_case`、クラスは `PascalCase`。引数と戻り値に型ヒントを付ける。
- 1ファイルに全部詰め込まない。機能ごとに分ける。最初から細かく分けすぎない。
- 実行は `server/.venv` を有効にしてから。追加パッケージは入れず、標準ライブラリのままにする。足したいときは名前と理由を人間に伝える。

## 6. Git

- AI は git を自律実行しない。`commit` / `push` / `pull` / `merge` / `rebase` / `reset` / `checkout` / `stash`、ブランチ、PR、`--force` は行わない。人間が `scripts/sync_pull.ps1` / `scripts/sync_push.ps1` を使う。人間が「push して」「pull して」と言ったときだけ、そのスクリプトを実行する。
- 谷野ルールのオーディション（採用者だけ全ファイルを1コミット、不採用は `git reset --hard`）は使わない。この期間の作業は、既存の作品を1本に仕上げる。
- `.gitignore` は編集しない。変更が必要なら人間に伝える。

## 7. 報告

実装の完了報告は、この4見出しをこの順で書く。各項目は短く、結果だけ書く。

```
## できたこと
## できていないこと・残っていること
## 成果物の確認方法（起動コマンド / 開く URL / 見るべき画面）
## ホストにやってほしいこと
```

- 「ホストにやってほしいこと」が無いときは「なし」と書く。
- 画面で何が変わったかを書く。関数名を並べて経緯を説明しない。
- 動作確認は、実行したコマンドと、画面に見えたことを入れる（`_template`）。
- 確認が要るものはホストに聞く。コンセプトの解釈が割れるとき、外部 API やライブラリを使うとき、共有ファイルを変えるとき、公開 URL を足すとき、`.gitignore` や `agent_rule.md` を変えた方がよいとき。
- `docs/conversation_log/` には、`agent_rule.md` §7 どおり、人間の指示原文と、返した本文を残す。
- 作業メモ `docs/agent_docs/` には、やったこと、動作確認、未完了、ライブラリや共有ファイルの依頼を残す。
