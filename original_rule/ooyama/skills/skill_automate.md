# Automation の作成（対話型）

このスキルは、ユーザーが新しい **Cursor Automation** を作りたい・構築したい・セットアップしたい・作成したいと明示的に述べたときに使用します。例:「Cursor の automation を作って」「このドラフトで Automations エディタを開いて」「スケジュール実行される Cursor エージェントをセットアップして」など。

**曖昧さの解消。** ユーザーのワークスペースにおける「自動化 (automation)」は多くの意味を持ちえます（`.github/workflows`、CI パイプライン、スケジュールジョブ、スクリプト、dbt、ブラウザ自動化、シェルスクリプト、ワークフローエンジン）。「これを自動化して」「デプロイの自動化を手伝って」「automation を作って」のような一般的なフレーズが **Cursor Automation** を意味すると想定**しない**でください。ユーザーが特定のサーフェスに言及した場合はそのサーフェスにルーティングし、コンテキストが別の場所を指している場合は通常のリポジトリ/プロダクト探索を行い、対象サーフェスが曖昧な場合は短い確認質問をしてください。このスパイン（実行の背骨）を開始するのは、ユーザーが Cursor Automations を明示的に依頼した場合、または Cursor Automations が意図したサーフェスであると確認した場合のみです。

## 実行スパイン（毎回の実行）

1. **完了パスの確認。** まず、アプリ内 Automations エディタへのハンドオフが利用可能かを確認します（下記の**完了手段の可用性**を参照）。Automations エディタツールもリソースオープナーも利用できない場合は、即座に「このスキルは Agents Window で使用してください。」と伝えて停止します。
2. **意図の把握 + 積極的なインテグレーション探索。** 完了パスの確認が通過した後、プロンプトに {何がきっかけになるか、何が起こるべきか、どんな成果か} のうち 2 つ以上が欠けている場合は、1〜2 文の説明を求める短いプレーンチャットのメッセージを 1 通送って待ちます。プロンプトがすでにトリガー + アクション + 成果を示している場合はスキップします。ユーザーが名指しした、または示唆したインテグレーションについては積極的に探索を実行します — cwd での `gh repo view`、Slack MCP のチャンネル、PagerDuty MCP のサービス、Linear/Sentry MCP のチーム/プロジェクト。結果を使って後の質問を省略します。
3. **完全性ゲート。** 下記のトリガー、ツール、プロンプト、命名、PCD のチェックを順に進めます。ユーザーが明示的に Automations エディタへ先送りした場合を除き、ピッカー由来の必須フィールドが不明なままサマリーへ飛ばないでください。
4. **1 回に統合した質問。** インテグレーション探索で解決できなかったもの — トリガーの詳細、曖昧な場合のリポジトリ / チャンネル / サービス、自明でない場合のツール — をインラインでまとめて尋ねます。デフォルトはプレーンチャットのインライン質問です。`AskQuestion` へエスカレートするのは、(a) ツールの複数選択と、(b) 3 件以上の候補があるインテグレーション探索の候補リスト、の場合のみです。
5. **ドラフトテーブル → 承認 → 完了ハンドオフ。** 名前 / 説明、トリガー、ツール、指示、解決済み設定、「エディタで仕上げる項目」を平易な言葉でまとめたコンパクトな Markdown テーブル（YAML なし）を表示します。ユーザーが承認したら、先送りした値をエディタで仕上げられるよう Automations エディタを開いてよいか尋ねます。ユーザーが「はい」と答えたら、可用性チェックで決まった完了パスを使用します。

## ハウスルール

- **平易な言葉のみ。** ユーザーに見えるチャットで、MCP / ツール / proto の名前、リクエストタイプ、enum 値、ステージラベル、生の CLI 出力を表示したり話題にしたりしないこと。「ドラフトでエディタを開きます」「Slack チャンネル」「リポジトリとブランチ」のように言います。例外: ユーザーが内部情報の表示を明示的に求めた場合。
- **最終確認に YAML を出さない。** ドラフトテーブル = 平易な言葉によるコンパクトな Markdown のみ。YAML / JSON は内部で構築・検証し、ワイヤーペイロードはユーザーが求めた場合にのみ表示します。
- **自動フォールバック禁止。** 勝手に送信する、URL を開く、ブラウザのプレフィルリンクを貼る、バケットを切り替える、といったことは絶対にしないこと。唯一の完了パスは、レビュー済みドラフトテーブル → ユーザー承認 → ユーザーの準備完了確認 → Automations エディタを開く、の流れです。Automations エディタツールもリソースオープナーも利用できない場合は、即座に停止し、このスキルを Agents Window で使うようユーザーに伝えます。
- **作成専用。** このスキルは新規 automation の準備のみを行います。チャットから既存の Cursor Automations を一覧・取得・調査・更新・検索しないこと。
- **インテグレーション探索は許可。** Slack チャンネル、PagerDuty サービス、Linear チーム、Sentry プロジェクトなど、ピッカー由来のインテグレーション値については、接続済みインテグレーションの MCP の read / list / search ツールを使用できます。これには、Cursor Automations を一覧・取得・調査・作成・更新・完了・プレフィルするバックエンド automation ツールは**含まれません**。
- **リポジトリファイルの参照。** ドラフトのどのフィールド（プロンプト、指示、名前、説明）でも、チャットの現在のリポジトリのファイル（パス、抜粋、`@file` メンション）を参照してよいのは、次の**両方**が真の場合のみです: (1) その automation が同じリポジトリで実行される（git トリガーのスコープまたは `workflow.gitConfig.repo` がチャットのリポジトリである）こと、**かつ** (2) そのファイルがそのリポジトリにコミット済みである（automation がチェックアウトするブランチ上で `git` に追跡されており、単にワーキングツリーに存在するだけではない）こと。どちらかの条件を満たさない場合は、パスや内容を埋め込まず、意図を言い換えるか、先にファイルをコミットしてプッシュするようユーザーに依頼してください。未追跡 / ステージのみ / dirty のみのファイル、automation のリポジトリ外のファイル、チャットのチェックアウトと異なるリポジトリのファイルは、いかなる場合も対象外です。

## PCD — ポータルの完全性と先送り

エディタを開く前にドラフトを完全な状態に保つため、これらのチェックを使用します。この Id をユーザーに表示しないこと。

| Id | スコープ |
|----|-------|
| **PCD:slack-trigger** | `slackTrigger` のチャンネル選択。今チャンネルを指定するか Automations UI で選ぶかを尋ねます。探索または明示的な UI への先送りが、ドラフトテーブルの前に済んでいる必要があります。 |
| **PCD:slack-actions** | `slack` / `readSlack` アクション。ドラフトテーブルの前に、送信先を尋ねるか、エディタへの明示的な先送りを確認します。 |
| **PCD:git-scope** | `git` の PR / push / CI トリガー。リポジトリ/組織/ブランチのスコープを解決するか、エディタへ明示的に先送りする必要があります。 |
| **PCD:universal** | 意図的に残したギャップはすべて、ドラフトテーブルの「エディタで仕上げる項目」行に載せ、最終ハンドオフのメモでも繰り返します。 |

### PCD マトリクス

| スコープ | 先送りしない限り、エディタを開く前に満たすこと |
|-------|---------------------------------------|
| **PCD:slack-trigger** | Slack チャンネル ID が解決済みであるか、ユーザーが Automations UI でチャンネルを選ぶことを選択している。空のチャンネルが有効なのは、明示的な UI への先送りの場合のみ。 |
| **PCD:slack-actions** | `slack.channel` / readSlack のスコープが解決済みであるか、ユーザーがエディタで **Select channels** を選択している。ID は `C…` / `G…` でなければならず、`U…` は不可。`D…` の ID は `slack` アクションでのみ有効で、常に automation オーナーとの DM に解決される。 |
| **PCD:git-scope** | PR トリガーにはリポジトリ/組織があり、push トリガーにはリポジトリ + ブランチがあり、CI トリガーにはリポジトリスコープがあること。スコープを絞ったリポジトリ探索は、ユーザーが対象を特定した後にのみ使用する。 |

### PCD の注意点

- Slack トリガーと Slack アクションの送信先は別々の質問です。Slack トリガーがあるからといって Slack アクションの送信先が決まるわけではなく、Slack アクションがあるからといって Slack トリガーのチャンネルが決まるわけでもありません。
- ユーザーが「今指定する」を選んだ後は、探索を実行したかユーザーが明示的にエディタへの先送りに切り替えた場合を除き、空の Slack チャンネル値をプレフィルしないこと。
- Slack への返信については、「トリガーとなったスレッドで返信する」と「特定のチャンネルまたは DM に送信する」を別々の選択肢として提示します。
- `mcp` を有効にする場合、そのサーバーは下記の **MCP 存在ゲート**と **MCP 認証ゲート**を通過している必要があります。カタログ上の正確なサーバー名は可能な限り自分で発見・選択し、リクエストに合致する使用可能なカタログ候補が複数ある場合や、要求されたインテグレーションが曖昧な場合にのみユーザーに尋ねます。これを Cursor プラグインと呼ばないこと。サーバー名を捏造しないこと。

### MCP 存在ゲート

MCP サーバーが適格となるのは、現在のユーザーが利用可能な MCP/ツールカタログによって、それがこのセッションで存在し使用可能であることが証明される場合のみです。インテグレーション探索に MCP を使う前、またはドラフトに `mcp` アクションを追加する前に、エージェントセッションに公開されている実際のカタログを調べ、`mcp.server.name` に入れる正しい値を選択します。

**カタログの正しいフィールドを読むこと。** エージェント側のカタログエントリは `~/.cursor/mcps/<folder>/SERVER_METADATA.json` にあり、2 つの異なる値を持ちます:

- `serverIdentifier` — エージェントランタイムが使うスコープ付きフォルダ名（例: `dashboard-team-1-Linear`、`plugin-pagerduty-pagerduty-mcp`、`cursor-app-control`）。
- `serverName` — ユーザーが cursor.com 上で設定した素の名前（例: `Linear`、`pagerduty-mcp`、`Databricks SQL`）。

`workflow.actions[].mcp.server.name` および `@[MCP: ...]` 形式のプロンプトメンションには `serverName` を書きます。`serverIdentifier` / フォルダ名を書かないこと、プレフィックス（`team-…`、`user-…`、`<orgId>-…`）を捏造・言い換えしないこと、フォルダ名からプレフィックスを手作業で削らないこと — 多くの `serverName` にはスペースが含まれる（例: `Databricks SQL`、`statsig read only console`）ため、識別子の文字列加工は壊れやすいのです。Automations エディタはトリム + 小文字化でマッチングするため大文字小文字は問題になりませんが、それでも `SERVER_METADATA.json` の正確な `serverName` を渡してください。有用な URL がある場合は、`templateMcpHints: [{ name: <serverName>, url: <serverUrl> }]` も渡すことで、名前のずれを URL マッチで救済できます。

**適格性 — ダッシュボード連携サーバーのみ。** Automations エディタの `GetAvailableMcpServers` レスポンスに現れるのはダッシュボード連携サーバーのみで、エディタはこれを使ってプレフィルされた `mcp` アクションを接続済みサーバーに解決します。それらの `serverIdentifier` は必ず次のいずれかのプレフィックスで始まります:

- `dashboard-team-<teamId>-`（チーム共有サーバー）
- `dashboard-`（cursor.com でユーザーが設定した個人サーバー）
- `plugin-<slug>-`（マーケットプレイスのプラグインサーバー）

エージェントカタログ内のそれ以外 — `cursor-ide-browser`、`cursor-app-control`、`extension-…`、プロジェクトの `mcp.json` サーバー、その他のローカルサーバー — はダッシュボードカタログには現れません。これらは `mcp` アクションに対して不適格として扱います: `workflow.actions` に追加しない、`@[MCP: ...]` プロンプトメンションで参照しない、エディタを開いたときに解決されると想定しない。不適格なサーバーをプレフィルすると、その行はブロックされた「Set up MCP」状態になり、ユーザーが保存できなくなります。

ユーザーが要求したインテグレーションに、使用可能でダッシュボード適格なカタログサーバーが 1 つ明確に一致する場合は、ユーザーにサーバー名の綴りを尋ねずにそれを使用します。ユーザーのプロンプト、スクリーンショット、スキルファイル、ワークフローテンプレート、マーケットプレイスのドキュメント、社内慣習に出てくる名前は証明にはなりません。

カタログに使用可能でダッシュボード適格なサーバーが含まれていない場合は、その MCP を呼び出さず、その `mcp` アクションを追加せず、`@[MCP: ...]` プロンプトメンションも含めないこと。存在しない、無効化されている、まだセットアップが必要なサーバーは、プレフィルにおいて利用不可として扱います。先にセットアップするようユーザーに依頼するか、その MCP をドラフトから外し、**エディタで仕上げる項目**に「Automations エディタで <インテグレーション> をセットアップ/選択する」と記録します。不明な MCP サーバー名は、先送りツール行として有効ではありません。プレフィルされた存在しない MCP は保存をブロックするためです。

### MCP 認証ゲート

**このゲートが存在する理由。** Automations エディタは MCP OAuth を促すことができますが、そのフローはドラフトから離れて遷移するため、ユーザーは作業中の変更を失います。`mcp` アクションを追加する前、ドラフトテーブルを表示する前、エディタを開く前に、チャット内で MCP を認証してください。

**適用タイミング。** ダッシュボード適格なサーバーに対して `mcp` アクションまたは `@[MCP: ...]` プロンプトメンションを追加する予定があるときは、必ずこのゲートを実行します — ピッカー由来の値のためのインテグレーション探索の後を含みます。

**未認証サーバーの検出**は現在のセッションカタログから行います（推測しないこと）。`STATUS.md` は認証と一般的なエラー状態の両方で書き込まれるため、ファイルが存在するだけでは認証シグナルには**なりません** — ファイルを読んで内容を確認してください:

- `~/.cursor/mcps/<folder>/STATUS.md` が存在し、**かつ**その内容がサーバーは認証が必要だと述べている（例:「needs authentication」/ `mcp_auth` の呼び出しを指示している）。一般的なエラーを報告するだけの STATUS.md は認証シグナルでは**ありません**。
- `GetMcpTools`（または同等のカタログ調査）が、そのサーバーの `serverIdentifier` について `serverStatus: "needsAuth"` を報告している。
- そのサーバーのライブツールリストが `mcp_auth` のみ（他に使えるツールがまだない）。
- そのサーバーに対するインテグレーション探索が認証 / 認可エラーで失敗する。

存在ゲートを通過したが上記のいずれかの認証シグナルに一致するサーバーは**未認証**です — 「存在しない」「未セットアップ」「一般的なエラー」とは区別して扱います。

**認証されるまでハードストップ。** 対象の MCP が未認証の場合:

1. **automation ドラフト作成のスパインを停止します。** `mcp` アクションを追加せず、`@[MCP: ...]` メンションを含めず、ドラフトテーブルを表示せず、Automations エディタを開かないこと。
2. どのインテグレーションがまだ接続されていないかを**ユーザーに平易に伝えます**（`serverName` を使い、内部 ID は使わない）。今接続すればドラフトが安全に保たれること、Automations エディタへ認証を先送りすると未保存の作業が破棄されうることを説明します。
3. **可能ならインライン認証を提案します。** このスキルは Agents Window で実行され、対話的な MCP 認証がサポートされています。サーバーが `mcp_auth` を公開している場合（`GetMcpTools`、サーバーのツールリスト、または `STATUS.md` 経由）、今すぐ接続フローを開始してよいか尋ねます。同意を得たら、そのサーバーの `serverIdentifier` に対して `mcp_auth` を呼び出して**一度に 1 サーバーずつ**認証します（MCP ツールインターフェイス経由で引数は空、またはセッションの `McpAuth` ツールが列挙されている場合は `server_identifier` を指定）。成功を待ち、認証状態を再確認してから、ドラフト作成を再開します。
4. **インライン認証が利用できない場合**（このセッションに `mcp_auth` ツールがない場合）は、Cursor Settings → MCP でインテグレーションを接続し、その後ここに戻って準備ができたら知らせるよう案内します。MCP が未認証のままエディタを開かないこと。

**MCP の OAuth を Automations エディタに先送りしないこと。** プレフィルする予定の MCP について、「Automations エディタで <インテグレーション> を認証/接続する」を**エディタで仕上げる項目**に入れないこと。未認証のプレフィル済み MCP 行は保存をブロックし、エディタの認証リダイレクトはドラフトの状態を失わせます。

**認証成功後**は、認証ゲートを再実行し、その後インテグレーション探索とドラフト作成を続行します。サーバーが認証済みで使用可能になった場合にのみ、ドラフトに `mcp` ツールを含めます。

## 手順

### ステージ 0 — 完了手段の可用性（意図の把握より前に必ず実行）

**完了手段の可用性**（実行ごとに 1 回確認。これはエージェント内部の判断であり、ツール名をユーザーに引用しないこと）。このチェックをユーザーに言及しないこと。「まず、このセッションで Automations エディタへのハンドオフが利用可能か確認します」のようなことを言わないこと。Cursor バックエンドの automation ツールを調べないこと。古い完了パスを復元するために Cursor バックエンドの automation ツールのディスクリプタを調べないこと。

| バケット | シグナル | デフォルトの完了手段 |
|--------|--------|----------------|
| **Automations エディタ** | `cursor-app-control.open_automation` が列挙されている | レビュー済みドラフトで Automations エディタを開く |
| **Agents Window が必要** | `cursor-app-control.open_automation` も `cursor-app-control.open_resource` も列挙されていない | 即座に停止 —「このスキルは Agents Window で使用してください。」と伝える |

Automations エディタのパスは、レビュー済みドラフトで `open_automation` を直接使用します。バックエンドの automation 完了ツールを調査・呼び出ししない、ブラウザのプレフィル URL を構築・貼り付けしない、`open_resource` を呼び出さない、`cursor://` ディープリンクを構築しないこと。

`cursor-app-control.open_automation` も `cursor-app-control.open_resource` も利用できない場合は、automation ドラフト作成のフローを続行せず、ブラウザのプレフィル URL を生成せず、フォローアップの質問もしないこと。即座にユーザーへ「このスキルは Agents Window で使用してください。」と伝えます。

### ステージ 1 — 意図の把握（プレーンチャット、AskQuestion 不使用）

このステージは完了手段の可用性チェックが通過した後にのみ実行します。ユーザーのプロンプトの情報が薄い場合は、短いプレーンチャットのメッセージを 1 通送って**待ちます**:

> 「本題に入る前に、この automation に何をさせたいですか? 何がきっかけで、何が起こり、どんな成果になるでしょうか? 1〜2 文で十分です。作れるものの例が見たい場合はお知らせください。」

プロンプトがすでにトリガー + アクション + 成果をカバーしている場合、またはユーザーが「順を追って案内して」に類することを言った場合はスキップします。回答は自由形式です — この質問を `AskQuestion` でラップしないこと。ステージ 1 が発火するか意図的にスキップされる前に、リポジトリ探索を実行しないこと。

### ステージ 2 — オーサリングファネル

既存 automation の編集はこのフローではサポートされません。バックエンドの automation ツールを通じて既存の automation を一覧・取得・調査・更新・検索しないこと。automation の名前や説明で検索しないこと。ユーザーが既存の automation を変更したい場合は、Automations UI で直接編集するか、置き換え用の新しい automation を作成するよう依頼してください。チャットから変更が保存されたと主張しないこと。

Automations UI の順序で作業します: トリガー → ツール → プロンプト → 名前/説明 → ドラフトテーブル。過去のメッセージからギャップを埋めます。ユーザーのプロンプトが必要なフィールドをすでにカバーし、PCD ゲートが満たされているか明示的に先送りされている場合を除き、直接 YAML に飛ばないこと。

#### トリガー

**付録 — トリガー選択テーブル**を使ってトリガーとフォローアップを選びます。ピッカー由来の値は、尋ねる前にインテグレーション探索で解決します。まだ回答されていないフィールドについてのみ尋ねます。スケジュールが未解決の cron トリガーは直接保存には無効です。webhook トリガーは、URL / 認証のため保存後に必ずエディタへ戻ります。

#### スケジュール時刻

cron が保存するのは単一の式であり、タイムゾーンの別フィールドはありません。ユーザーが cron フィールドにきれいにマップできるスケジュールを与えた場合（例:「平日の毎日午前 3 時」「毎日午前 9 時」「毎週月曜午前 9 時」）、エディタのプレフィルに cron トリガーを含めます。「私のタイムゾーンで」「現地時間で」は、時/曜日のパターン自体が cron で表現可能な限り、ユーザーが望む表示時刻の意図として扱います。`workflow.triggers` を空のままにしてスケジュールをプロンプトだけに書くことはしないでください。

ユーザーが述べた現地時間が、Automations エディタが表示する形と正確に一致するようにエンコードできない場合は、生の cron にタイムゾーンのヒントを添えて渡すことはしないでください。エディタを開く前にスケジュールについてもう 1 問尋ねます。トリガーなしのスケジュール automation を開かないこと。`cron: {}` をプレフィルしないこと。これは無効です。

有効な cron の例:

```yaml
# Every hour
cron: { cron: "0 * * * *" }

# Every day at 9:00
cron: { cron: "0 9 * * *" }

# Every Monday at 9:00
cron: { cron: "0 9 * * 1" }

# Weekdays at 9:00
cron: { cron: "0 9 * * 1-5" }
```

#### ツール

ツールが自明でない場合は、構造化された複数選択で尋ねます:

| ラベル | YAML |
|-------|------|
| PR にコメントする | `prComment` |
| Slack に投稿する | `slack` |
| Slack を読む | `readSlack` |
| レビュアーをリクエストする | `requestReviewers` |
| チェックランを管理する | `manageCheckRun` |
| MCP サーバーを使う | `mcp` |

`slack` / `readSlack` を有効にする場合、ドラフト作成の前に Slack MCP 探索でチャンネルを解決するか、UI への先送りを記録します。`mcp` を有効にする場合は、まず MCP 存在ゲートと MCP 認証ゲートを実行します。`workflow.actions` に追加してよいのは、正確で認証済みかつ使用可能なカタログの一致のみで、`mcp.server.name` は一致したエントリの `SERVER_METADATA.json` にある `serverName` の値でなければなりません — フォルダ名 / `serverIdentifier` は不可です。要求された MCP が存在しないか未セットアップの場合は、プレフィルせず、ユーザーにセットアップを依頼するか、セットアップ/選択をエディタへ先送りします。存在するが未認証の場合は、MCP 認証ゲートに従って停止します — プレフィルせず、OAuth をエディタへ先送りしないこと。

#### プロンプト + 名前

「[トリガー]のとき、エージェントは何をすべきですか?」と尋ねます。デフォルトは引き締まった 1 段落。ユーザーがより長く書いた場合はその長さに合わせます。クラウドのコンピュートは [Cloud Agent dashboard](https://cursor.com/dashboard?tab=cloud-agents) で設定します。これまでの回答から、名前と 1〜2 文の説明を提案します。

#### ファストパス

確信度が高く必須フィールドが揃っている場合は、ドラフトテーブルへ直接スキップして構いません。ただし、Slack チャンネルの選択、Git のリポジトリ/ブランチスコープ、`mcp.server.name`、未解決のスケジュール、MCP 認証ゲートをスキップするためにファストパスを使ってはいけません — ファストパスは**認証されるまでハードストップ**ルールを決してバイパスせず、プレフィルされた MCP が未認証のままドラフトテーブルを表示することはできません。不確かな場合は、質問票全体を再演するのではなく、焦点を絞った質問を 1 つします。

### ステージ 3 — ドラフトテーブル、検証、完了

ドラフトを平易な言葉のコンパクトな Markdown テーブルとして要約します。計画書、チェックリスト、「これから行うステップ」を書かないこと:

| ドラフト項目 | エディタで開かれる内容 |
|-------------|------------------------------|
| 名前 / 説明 | 短い平易な言葉の値 |
| トリガー | automation を開始するもの |
| ツール | 有効化された機能 |
| 指示 | プロンプトの挙動の要約 |
| 解決済み設定 | リポジトリ / ブランチ、Slack チャンネル、サービス / プロジェクト、スケジュール、その他のピッカー由来の値 |
| エディタで仕上げる項目 | Automations UI に先送りした設定。何もなければ "None" と書く |

「これで正しいですか?」で締めます。YAML や JSON のブロックを付け足さないこと。承認後、内部の**検証チェック**を実行し、その後、完了ハンドオフの確認を送ります。ドラフトへの単なる「はい」はドラフトを承認しますが、最終的な準備完了の確認の代わりにはなりません。

#### ガラスの完了パス（コンプライアンス）

`cursor-app-control.open_automation` が利用可能な場合、完了パスはちょうど 1 つです:

1. Markdown のドラフトテーブルを表示する。
2. ユーザーの承認を待つ。
3. Automations エディタで仕上げる必要のある値、セットアップ、webhook/認証の詳細をユーザーに伝える。「開く準備はいいですか?」のような直接的な準備確認の質問をする。
4. 確認が取れたら、レビュー済みドラフトで Automations エディタを開く。

保存、ブラウザ、リンク貼り付け、スキップ、フォールバックの選択肢を提示しないこと。

### 完了後のアクション（エージェント内部）

エディタを開く前、またはその他の方法でユーザーをチャットから離れさせる前に、先送りしたすべてのフィールドと、ハンドオフ後にユーザーが必要とする注意点をまとめた短い最終ハンドオフのメモを 1 通送ります。「エディタで仕上げる項目」のすべての行、インテグレーションのセットアップに関するメモ、webhook/認証のフォローアップ、Slack の DM/チャンネルピッカーの確認、Cloud コンピュートのメモ、意図的にエディタのピッカーに残したスケジュールを含めます。「開く準備はいいですか?」のような直接的な準備確認の質問で締めます。ユーザーが「はい」と答えたら、選択した完了パスを使用します。これらのリマインダーを開くステップの後に置かないこと。ユーザーはチャットを離れた後、チャットを見ないかもしれません。

- **ドラフトで Automations エディタを開く**（Automations エディタ）。新規 automation にのみ使用します。レビュー済みの WorkflowData JSON を `prefillWorkflowData` として `cursor-app-control.open_automation` を呼び出します。このバケットのために、バックエンドの automation ツール、`open_resource`、ブラウザ URL ビルダー、`cursor://` URL を呼び出さないこと。`open_automation` が失敗した場合は、失敗を平易な言葉で説明して停止します。
- **Agents Window が必要**。`cursor-app-control.open_automation` も `cursor-app-control.open_resource` も利用できない場合は、「このスキルは Agents Window で使用してください。」と伝えます。ドラフト作成、送信、ブラウザのプレフィル URL の貼り付け、パスの自動切り替えを行わないこと。

## リファレンス

### 尋ねる前に探索する

ピッカー由来の値（リポジトリ、Slack チャンネル / DM、GitHub/GitLab の PR / コメントスコープ、PagerDuty サービス、Linear チーム、Sentry プロジェクトなど）をユーザーに尋ねる前に、関連するインテグレーションの MCP や CLI が利用可能かつ認証済みかを積極的に確認し、関連レコードを取得します。MCP 連携のインテグレーションでは、可用性チェックは現在のユーザーの実際の MCP/ツールカタログに対して行い、記憶や推測のサーバー名を使わないこと。結果を次の質問に活かします: **1 件一致 → インラインで確認、2 件 → インラインで二択、3 件以上 → `AskQuestion` の単一選択。** スコープを絞ったインテグレーション探索を使い尽くすか、ユーザーが Automations エディタへの先送りを選んだ場合にのみ、自由形式で尋ねます。

**認証の境界。** 接続済みかつ認証済みの場合、インテグレーションの list / search / read ツール、`gh`、`glab` を呼び出せます。このパスを、Cursor Automations の一覧・取得・調査・作成・更新・完了・プレフィルに使わないこと。

- **`mcp` automation アクションに使う MCP インテグレーション**は上記の **MCP 認証ゲート**に従います — 停止し、説明し、プレフィルの前にチャット内で認証します。そのサーバーで列挙されている場合、Agents Window ではインライン `mcp_auth` がサポートされます。
- **その他のインテグレーション**（Slack チャンネル探索、PagerDuty サービス、`gh` / `glab` など）: 存在しないか利用できない場合、続行前にセットアップしたいかをユーザーに尋ねます。はいの場合はセットアップを案内し、準備完了の確認後に探索を再試行します。いいえの場合はドラフトを続行し、後で Automations エディタでそのインテグレーションのセットアップを仕上げる必要があることを伝えます。これら非 MCP アクションのインテグレーションに限り、明示的な**セットアップ後に再試行**の確認なしに `mcp_auth` を呼び出さないこと。

#### GitHub / GitLab のリポジトリスコープ

自然なリポジトリの呼び名を受け入れます。最初に `owner/repo` 形式を要求しないこと、スコープを絞った CLI 探索を試す前にリポジトリの列挙をユーザーに求めないこと。順序:

1. **正確な指定または現在のリポジトリ。** ユーザーが正確な `owner/repo` を与えた、「このリポジトリ」と言った、または現在のチェックアウトが明らかな対象である場合、`gh repo view owner/repo --json defaultBranchRef,nameWithOwner` または `gh repo view --json defaultBranchRef,nameWithOwner` でリポジトリ + デフォルトブランチを取得します。GitLab では、利用可能なら同等の `glab repo view` / プロジェクト表示コマンドを使います。正確な参照が認証エラーで失敗した場合にのみ、認証状態を確認します。
2. **複数の候補が名指しされた場合。** ユーザーが複数のリポジトリ候補を名指しした場合、スコープなしの検索を実行しないこと。正確な `owner/repo` の候補は個別参照で解決し、共通のオーナー/組織/ネームスペース、現在のチェックアウト、プロダクトのコンテキストで検索が絞れる場合にのみ、スコープを絞った探索を実行します。スコープ付きの参照が使えない場合は、CLI 参照の前に、ユーザーが名指ししたリポジトリ + **Automations UI で選ぶ** を選択肢とした `AskQuestion` を使います。
3. **ユーザーの選択が必要な場合。** ユーザーがリポジトリを選ぶ必要があり、オーナー/組織/ネームスペース、呼び名、現在のチェックアウト、プロダクトのコンテキストで検索を絞れる場合は、尋ねる前に候補を積極的に取得します: `gh search repos "<nickname> in:name" --json fullName,description --limit 10`、スコープ付きの `gh repo list <owner-or-org> --json nameWithOwner,description --limit 20`、または同等のスコープ付き `glab repo list` / プロジェクト検索。次のステップがユーザーに選んでもらうことである場合でも、これを行います。
4. **候補の提示。** 探索結果またはユーザーが名指しした候補セットを次の質問で使います: 1 件一致 → インラインで確認、2 件 → インラインで二択、3 件以上 → 返された/名指しされたリポジトリ + **Automations UI で選ぶ** を選択肢とした `AskQuestion`。検索/一覧の探索後もリポジトリの選択が曖昧な場合は、自由形式のリポジトリ質問ではなく、部分一致 + UI への先送りを選択肢とした `AskQuestion` を使います。
5. **ブランチの確認。** 利用可能なら参照結果のデフォルトブランチを使います。automation が特定のブランチを必要とし、探索で解決できなかった場合は、ブランチを尋ねるか、デフォルトブランチを明示的に提案します。
6. **探索が失敗または利用不可の場合。** `gh` / `glab` が存在しない、未認証、利用不可、またはスコープ付きの参照/検索/一覧が失敗した場合、どのリポジトリとブランチを使うか、または Automations UI で選ぶかをユーザーに尋ねます。ユーザーが**セットアップ後に再試行**を選ばない限り、CLI のセットアップでブロックしないこと。

ガードレール: プライベートリポジトリの広範な棚卸しや、スコープなしのアカウント/組織全体のスイープを実行しないこと。`gh repo list` / `glab repo list` はオーナー/組織/ネームスペースなど十分に狭いコンテキストにスコープを保つこと。生の `git remote` 出力を唯一の真実の情報源として使わないこと。

#### Slack

`slackTrigger` / `slack` / `readSlack` が関係するときは毎回、チャンネルの質問の前に Slack MCP 探索を行います。**今指定する**とは、エージェントがまず探索を実行することを意味します — 「ユーザーに ID を尋ねる」ことではありません。1 チャンネル → インラインで確認、2 件 → インラインで二択、3 件以上 → 返されたチャンネル（+ **Automations UI で選ぶ**）を選択肢とした `AskQuestion`。**「今指定する」の後、探索も continue-without もなしに空のチャンネルでプレフィルしないこと。** 探索がブロックされた場合 → **セットアップ後に再試行** / **MCP なしで続行** / **Automations UI で選ぶ** をインラインで提示します。

Slack の `channel` は `C…` / `G…` のチャンネル ID を受け付けます — `U…` のメンバー ID は不可。`slack` **アクション**では `D…` の ID も受け付けられ、常に automation オーナーとの DM に解決されます（他ユーザーへの DM はサポートされません）。`D…` の ID はトリガーでは拒否されます。Slack への返信については、**トリガーとなったスレッドで返信する**と**特定のチャンネルまたは DM に送信する**を別々に提示します。ユーザーがエディタで **Select channels** を選ぶ場合、空の `{}` アクションは有効です。先送りをドラフトテーブルに記録してください。

#### PagerDuty / Linear / Sentry

`serviceIds` のスコープを決める前に PagerDuty MCP でサービスを一覧します: 1/2 件はインライン、3 件以上 → サービスを選択肢とした `AskQuestion`。**`serviceIds` は任意** — 指定しない場合は UI へ先送りします。Linear のチーム / プロジェクトと Sentry のプロジェクトも同じパターンに従います: MCP が接続済みなら探索し、そうでなければエディタへ先送りします。

### YAML 出力の形（エージェント内部）

ワイヤーフォーマットは、`prefillWorkflowData` として `open_automation` に渡すレビュー済み Automations ドラフトと一致します — 完全な enum 名（例: `GIT_PULL_REQUEST_ACTION_OPENED`）を持つ正規の proto JSON です。PR のスコープは `git.pullRequest`（`repos` / `orgs`）にあり、`workflow.gitConfig` は、チェックアウトを必要とする非 `git` トリガーのための `repo` + `branch` を保持します。`ignoreDraftPr` ではなく `ignoreDraftPrs` を使うこと。Slack チャンネル ID: `C…` / `G…`。`D…` の ID（`slack` アクションのみ）は automation オーナーの DM に解決されます。

スケルトン:

```yaml
name: "My automation"
description: "Optional description"
workflow:
  triggers: []
  actions: []
  prompts: []
  model: ""
  agentOptions:
    skipInstall: false
  memoryEnabled: true
```

プロンプトには `|` ブロックスカラーを使います（`>-` の折りたたみは箇条書きを壊します）。フィールドが UI 専用の場合、空の `{}` アクションは有効です。`mcp` を有効にする場合 `mcp.server.name` は必須で、その名前は一致したエントリの `SERVER_METADATA.json` の `serverName` フィールドでなければなりません — フォルダ名 / `serverIdentifier` は不可。適格性フィルタとプレフィックス捏造禁止のルールについては MCP 存在ゲートを参照してください。

**トリガーの oneof キーは網羅的です。** `workflow.triggers` の各エントリは、次のトップレベル proto キーのうち正確に 1 つを使用しなければなりません: `cron`、`git`、`slackTrigger`、`slackReactionAdded`、`slackChannelCreated`、`emailReceived`、`microsoftTeamsTrigger`、`microsoftTeamsChannelCreated`、`linear`、`webhook`、`pagerduty`、`sentry`。捏造や言い換え（`slackReaction`、`slack_reaction`、`slack`、`reactionAdded` など）は絶対にしないこと — エディタは `ignoreUnknownFields: true` でトリガーをデコードし、不明なキーを黙って捨て、結果を設定不能な「Configure trigger」カードとして表示して保存をブロックします。空の `{}` トリガーエントリも同じ失敗モードに陥ります。完全に名前を特定できないトリガーは決してプレフィルしないこと。

### 検証チェック（エージェント内部）

ドラフトテーブルの承認後: チェックリスト + proto に対して YAML を検証します（PR の enum、`ignoreDraftPrs`、Slack ID のプレフィックス、必要な場合の `gitConfig` の存在、`mcp` 有効時の `mcp.server.name`、認証済みで使用可能なカタログ一致に裏付けられた MCP アクション、説明文に `__securitybot_metadata__` / `customInstruction` のメタデータマーカーが含まれないこと）。automation の YAML に対して**インラインの JSON スキーマバリデータ**やシェルスニペットを発明しないこと — proto の形からずれ、有効なドラフトを誤って不合格にしうるためです。検証に失敗した場合は、問題を平易な言葉で説明し、何を変更するか尋ねます。ユーザーが明示的に求めない限り、完全な YAML を貼り付けないこと。**バックエンドの automation ツールを使わず、リポジトリローカルのスクリプトをシェルで実行しないこと** — Automations エディタへのハンドオフには `open_automation` のみを使います。

**`slack`** — 質問:「どの Slack トリガーですか?」

| 選択肢ラベル | 選択肢 ID | YAML |
|--------------|-----------|------|
| チャンネルの新規メッセージ | `slack_message` | `slackTrigger` |
| メッセージへのリアクション追加 | `slack_reaction_added` | `slackReactionAdded` |
| チャンネル作成 | `slack_channel_created` | `slackChannelCreated` |

**`slackReactionAdded` のペイロード** — `{ channels: ["C…"], emojiName: "<name>" }`。`emojiName` は前後のコロン**なし**の Slack ショートネーム（例: `thumbsup` であって `:thumbsup:` ではない）。サーバーは保存時に Unicode 絵文字を対応するエイリアスに正規化します。`slackReactionAdded` トリガーでは完了リアクションはサポートされず（再帰してしまうため）、黙って破棄されます。

**`emailReceived` のペイロード**（Grok Bot 専用）— `{ inboxEmail: "<one of the user's Grok Bot inbox addresses>", fromAddresses?: ["a@b.com"], requireAuthPass: true }`。そのインボックスにメールが届いたときに発火します。`fromAddresses` は小文字化された送信者の完全一致許可リスト（空 = すべての送信者）で、`requireAuthPass`（デフォルト true）は SPF/DKIM/DMARC に失敗したメールをスキップします。どのルーチンにも一致しないメールは誰も起こしません。実行はエンベロープ（送信者、件名、ID）のみを受け取り、本文は `read_email_thread` で読みます。

**Slack メッセージトリガーでの完了リアクション。**「エージェントが完了したら `:foo:` でリアクションする」は、別のトリガーではなく `slackTrigger` 上の完了リアクションオプションです。同じ `slackTrigger` エントリに `slackCompletionReactionMode: SLACK_COMPLETION_REACTION_MODE_CUSTOM` と `slackCompletionReactionCustomEmoji: ":foo:"`（前後のコロン付き）を設定します。完了時の挙動を表現するために `slackReactionAdded` トリガーを作らないこと。

**「〜でリアクション」の曖昧さの解消。** ユーザーが「X のリアクションでトリガーする」と言った場合、トリガーは `slackReactionAdded`（`emojiName: "x"`、コロンなし）です。ユーザーが「完了したら X でリアクション」「完了時に」「成功後に」と言った場合、トリガーは上記の完了リアクションフィールドを持つ `slackTrigger` です。意図が曖昧なときは、推測せずに焦点を絞った質問を 1 つしてください。
