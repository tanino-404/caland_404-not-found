キャンバスは、IDE がコンパイルする単一の `.canvas.tsx` ファイルであり、ユーザーはそれをチャットの横に開くことができます。以下のワークフローに順番どおりに従ってください。

## ワークフロー

### 1. キャンバスを使うかどうかを判断する

トリガーは応答の形ではなく、**ユーザーの意図**です。こう自問してください: この出力を、チャットとは別の、**トランスクリプトの外にある独立した永続的なスタンドアロン成果物**として見られることは、ユーザーにとって有益か？出力が目的達成の手段にすぎない場合（下書きしたメッセージ、コード修正、別ツール上のダッシュボードなど）は、キャンバスを使いません。

**エージェントが新しいスタンドアロンの分析的アウトプットを生成するときはキャンバスを使う:**
- 定量分析やメトリクスの内訳（例:「500 リクエスト送信して何件失敗するか教えて」）
- データベースクエリから構造化された知見を導き出す、請求やアカウントの調査
- カテゴリー分けされた指摘を含むセキュリティ監査やアーキテクチャレビュー
- システム横断のデータ分析や重複レポート
- MCP ツール（Databricks、Datadog など）からの構造化データで、永続的なスタンドアロン成果物が納品物であるもの
- 財務分析、マージンの分解、利用トレンドレポート
- ユーザーが再訪・改良したい大きなテーブル

**以下の場合はキャンバスを使わない:**
- ユーザーが**特定のツール**での作業を求めている — 「Datadog ダッシュボードを作って」は Datadog のダッシュボードを渡すという意味であり、キャンバスではない
- ユーザーに**具体的な納品物**がある — 「サポート回答の下書きを作って」「このコードを直して」「この PR を作って」
- ユーザーが**既存の成果物の中で作業している** — HTML ダッシュボードの改良、既存ファイルの編集
- ユーザーが**的を絞ったデバッグ**や活発な開発を行っている場合。途中で構造化された知見が得られたとしても
- 不変のビジュアル出力が、永続的なスタンドアロン成果物ではなくトランスクリプトの中に属する場合
- 短い事実の回答、単発のファイル編集、簡単な確認の質問
- MCP ツールが別の納品物のための**中間ステップ**として照会される場合（例: サポート回答の下書きのために Stripe を照会する）

### 2. キャンバスを書く

**場所。** キャンバスは `/Users/<user>/.cursor/projects/<workspace>/canvases/<name>.canvas.tsx` に置きます。IDE は、正確にそのディレクトリ直下に書かれたキャンバスのみを検出します — サブフォルダー、別の拡張子、他の場所は認識されません。新しいキャンバスは、必ずファイル書き込みツールを使って正確にそのパスに `.canvas.tsx` ファイルを作成してください。パスを伝えたりチャットにコードを表示したりするだけで止まってはいけません。この管理された `canvases/` ディレクトリは Cursor 自身によって事前に用意されているものとして扱ってください: キャンバスファイルを直接そこに書き込み、書き込み前に `mkdir` でディレクトリを作成したり存在確認をしたりすることにターンを費やさ**ない**でください。他の目的でその内容を一覧すること（例: 既存キャンバスの確認）は問題ありません。環境内の絶対パス（ターミナル、トランスクリプト、最近閲覧したファイル）からワークスペースディレクトリを特定できない場合は、推測せずに `~/.cursor/projects/` を一覧してください。`.canvas.tsx` で終わる説明的なケバブケースのファイル名を使い、頭字語の大文字は保持し、それ以外は小文字にします。

**ファイルのルール:**
- キャンバス 1 件につき `.canvas.tsx` ファイルはちょうど 1 つ。ヘルパーファイル、スタイルファイル、補助モジュールは決して作らない。
- インポートは `cursor/canvas` から**のみ**。相対インポート、npm パッケージ、Node ビルトインは不可。
- トップレベルのコンポーネントをデフォルトエクスポートする。
- すべてのデータをインラインで埋め込む。**`fetch()` 禁止、ネットワーク呼び出し禁止。**

**空の状態を決して描画しない。** キャンバスは実際のコンテンツを表示するために存在します。セクション、チャート、テーブル、コンポーネントに表示すべきデータがない場合は、**それを省略**してください — プレースホルダーテキスト（「Add header here」「TODO」「Example」）、「No data」メッセージ、空配列、ゼロ埋めの行、空のチャート枠で描画してはいけません。元となるデータがないためにキャンバス全体が空になってしまう場合は、キャンバスを作らず、何が不足しているかをユーザーに伝えて提供を求めてください。

**すべてのプロットにラベルを付ける。** チャートとテーブルは自己記述的でなければなりません — キャンバスだけを見た読者が、何を見ているのかを正確に理解できる必要があります。すべてのプロットに以下を含めてください:
- **具体的な指標**を名指しするタイトル（「Metrics」ではなく「サービス別 API エラー率」）。
- 両軸に**単位付きの軸ラベル**（例:「日付」「レイテンシ (ms)」）。
- 複数の系列を表示する場合は、ソースデータにある正確な系列名を用いた**凡例**。
- 小さなキャプションによる**出典と期間**（例:「Source: Datadog · last 7 days」）。値が変換されたもの（平均、p95、正規化、平滑化）である場合は、ラベルにそう明記する。

**コンポーネントの探索:** 手書きのマークアップより、組み込みの `cursor/canvas` コンポーネントを優先してください。公開されている全インターフェース（コンポーネント、フック、prop の型、トークン）は `~/.cursor/skills-cursor/canvas/sdk/index.d.ts` とその同階層の `.d.ts` ファイルに宣言されています — 正確なエクスポート、prop の形、フックのシグネチャが必要なときは、推測せずにそれらを読んでください。存在しないエクスポートを参照することが、最もよくあるランタイムエラーです。

書きながら下記のデザインガイダンスを適用し、キャンバスを返す前に「納品前セルフチェック」を完了してください。

## デザインガイダンス

創造的であってください。SDK は表現力のある構成要素を提供します — コンテンツに最も適した組み合わせで自由に使ってください。ただし slop（雑な出力）は避けること: グラデーション禁止、絵文字禁止、box-shadow 禁止、虹色の配色禁止。Cursor のキャンバスはフラットでミニマル、そして目的志向です。

### 視覚的な階層

すべてを同等に扱うべきではありません。主要なコンテンツにはより多くのスペース、より大きな見出し、アクセントカラーを与えます。補助的なコンテンツはコンパクトに保ちます。スクイントテスト: 目を細めて見たとき、何が重要かが分かりますか？

**色。** すべての色は `useHostTheme()` のトークンから取得します — 戻り値の形と使用パターンについては、SDK の宣言ファイル内の JSDoc を読んでください。ハードコードされた 16 進カラーは不可。アクセントカラーは意図をもって使い、すべてに使わないこと。

### slop パターン — 禁止事項

以下の特定のパターンは低品質な出力を生みます。2 つ以上が存在する場合は、デザインをやり直してください。

- **グラデーション** — `linear-gradient`、`radial-gradient`、`background-clip: text` は不可。
- **絵文字** — アイコン、ステータス表示、箇条書き記号、セクションマーカーとしての絵文字は不可。
- **ボックスシャドウ** — `box-shadow` は不可。フラットなサーフェスのみ。
- **同一カードの羅列** — すべてのセクションを変化のない同じカードスタイルで囲むこと。開いたセクションとカードを混ぜること。
- **虹色の配色** — 要素ごとに異なる色を付けること。ほとんどの要素はニュートラルにし、色は目的をもって控えめに使う。
- **巨大なテキスト** — H1（24px）を超えるフォントサイズや、CardHeader に詰め込まれた太字テキスト。
- **装飾的なボーダー** — すべての要素に色付きボーダーを付けること。ボーダーは構造的なもの（控えめなストロークトークン）であり、装飾ではない。

### 納品前セルフチェック

キャンバスのコードを返す前に、以下を確認してください:
1. レイアウトに視覚的な階層があるか。ひとつのものが際立っているべき。
2. 構成に多様性があるか。均一なブロックの単一カラムだけになっていないか。
3. slop チェック: 上記の禁止パターンをスキャンする。

## キャンバスの紹介

ユーザーにキャンバスへ言及するとき — 作成したもの、更新したもの、開いてほしいもののいずれでも — は、**必ず**その `.canvas.tsx` ファイルへの Markdown リンクを、完全な絶対パスを使って含めてください（例: `[Billing Review](/Users/<user>/.cursor/projects/<workspace>/canvases/billing-review.canvas.tsx)`）。リンクテキストには短い説明的なラベルを使います。リンクなしで名前やパスだけでキャンバスに言及してはいけません。

キャンバスを作成したときは、チャットの応答に、チャットの横に開けることを伝える短い一文を、そのリンクとともに追加してください:

- **最初のキャンバス** — ワークスペースの `canvases/` ディレクトリに他の `.canvas.tsx` ファイルが存在しない場合は、キャンバスとは何かを説明する一文を含める。
- **依頼されていないキャンバス** — ユーザーがキャンバスを求めていなかった場合は、プレーンテキストではなくキャンバスを選んだ理由を説明する一文を含める。

両方が同時に該当することもあります。合計で 1〜2 文あれば十分です。2 回目以降のキャンバスでは、そのキャンバスに再度言及する場合を除き、紹介文は省略します（その場合もリンクは付けます）。

## トラブルシューティング

キャンバスが空白に見えたり見つからなかったりする場合、最も多い原因は、正確に `/Users/<user>/.cursor/projects/<workspace>/canvases/` 配下に書き込まれていないことです — そのパスに保存し直してください。管理されたディレクトリを手動で作成しようとしてデバッグしないでください。ファイルパスの修正に集中してください。ユーザーは、Cursor の他のファイルパスと同様に、応答内のキャンバスファイルのパスをクリックして開くことができます。キャンバスを編集するたびに、ツール結果に `Canvas TypeScript check` の行が返り、そのファイルの現在の型エラー（または「no errors」）が報告されます — これを信頼できる診断シグナルとして扱ってください。
