# Loop

`/loop` を定期的または可変の間隔で実行します。まず、利用可能なツールからどちらの仕組みを使うかを判断し、以下の該当セクションのみに従ってください:

- `cursor-subscriptions-subscribe_timer` MCP ツールが利用可能な場合（Cloud Agent の場合）は、**サブスクリプションタイマー（クラウド）** を使います。ローカルの `sleep` ループはクラウドでは動作しません。
- それ以外（ローカルの IDE / CLI セッション）の場合は、**監視付きシェル出力（ローカル）** を使います。

## パース

`/loop [interval] <prompt>` を受け付けます。

- 先頭に間隔を置く形: `5m /foo`、`30s check status`、`2h run report`。
- 末尾に間隔を置く形: `check deploy every 5m`、`run tests every 10 minutes`。
- 間隔なし: 動的モード。エージェントが遅延時間を選び、tick ごとに変更してもよい。
- プロンプトが空: `Usage: /loop [interval] <prompt>` を表示する。

間隔は `30s`、`5m`、`2h`、`1d` のような形式を使います。単位を表す単語は短い単位表記に変換します。ユーザーが cron 形式のフレーズ（「毎平日の朝 9 時」など）を指定し、サブスクリプションタイマーの仕組みを使う場合は、遅延時間ではなく cron 式として渡します。

# サブスクリプションタイマー（クラウド）

`cursor-subscriptions` MCP タイマーを使い、`cursor-subscriptions-subscribe_timer` によってこの Cloud Agent を定期的なスケジュールで起こします。

## スケジュール

`cursor-subscriptions-subscribe_timer` を以下の引数で呼び出します:

- `name`: 安定したハンドル。プロンプトから導いた `loop-<purpose>` のような名前（例: `loop-check-deploy`）。サーバーは name で重複排除を行い、重複ヒット時は **古い設定を黙って維持します** — 下記「既存タイマーの変更」を参照。
- `prompt`: 各 tick でエージェントが受け取るべきフォローアップ文言そのもの。
- `delaySeconds`（正の整数、発火間の固定間隔）または `cron`（cron 式）のいずれか一方のみ。

最初のサーバー tick がコールドスタートにならないよう、プロンプトをまず 1 回すぐに実行します。その後サブスクライブし、次の内容を確認として伝えます: 間隔、プロンプトを既に 1 回実行済みであること、返された `subscriptionId`、停止するまで各 tick でループが発火し続けること。

以降の各 tick は通常のフォローアッププロンプトとして届きます。クライアント側では何も仕掛けないでください。サブスクライブ解除するかタイマーが期限切れになるまで、サーバーが発火し続けます。

## 既存タイマーの変更

`subscribe_timer` は既存タイマーをその場で更新 **しません**。同じ `name` の稼働中タイマーが既に存在する場合、サーバーは現在の `subscriptionId` を `created: false` で返し、**いま渡した `prompt`、`cron`、`delaySeconds` を破棄します**。これらを実際に変更するには、まず現在の `subscriptionId` に対して `cursor-subscriptions-unsubscribe` を呼び、その後で新しい値を指定して `cursor-subscriptions-subscribe_timer` を呼びます。

## 動的スケジュール

ユーザーはエージェントに自らペース配分してほしい場合です。`cursor-subscriptions` は `cursor-subscriptions-subscribe_github_ci` や `cursor-subscriptions-subscribe_origin_ci` で CI チェックを監視できますが、ファイル変更やログ行のような任意のシグナルに対するイベント監視の仕組みはありません。そうしたシグナルに対しては、時間間隔だけが調整手段です。

1. **プロンプトをいますぐ実行する。**
2. 最初に選んだ `delaySeconds` で 1 回サブスクライブする。
3. 各 tick で、次に望む間隔に変更がなければ何もしない — タイマーは発火し続ける。
4. ペースを変えるには、**先にサブスクライブ解除**（現在の `subscriptionId` で `cursor-subscriptions-unsubscribe`）し、その後同じ `name` と新しい `delaySeconds` で `cursor-subscriptions-subscribe_timer` を呼ぶ。解除を省くと黙って無視される: サーバーは既存のサブスクリプションをそのまま返し、新しい `delaySeconds` を無視する。

## 停止

1. `cursor-subscriptions-list_subscriptions` を呼び、name が `loop-<purpose>` に一致する行を探す。
2. その `subscriptionId` で `cursor-subscriptions-unsubscribe` を呼ぶ。
3. ループが停止したこととその理由を伝える。別のタイマーを仕掛けないこと。

複数のタイマーが目的に一致して判別できない場合は、候補をユーザーに提示し、どれを停止するか尋ねてください。

## 指針

- 無関係なタイマー同士が衝突しないよう、ループごとに一意の `name` を使う。
- ローカルの `sleep` ループやバックグラウンドシェルによる起床は開始しない — クラウドでは動作しない。
- 稼働中タイマーに対して同じ `name` で再登録しても黙って無視される — 新しい `prompt` / `cron` / `delaySeconds` は破棄される。稼働中タイマーの何かを変更するには、まずサブスクライブ解除する。
- 停止時に別のタイマーをスケジュールしない。

# 監視付きシェル出力（ローカル）

定期的なローカル作業のためにエージェントを起こすには、監視付きシェル出力を使います。

## 固定スケジュール

```bash
while true; do
  sleep <seconds>
  echo 'AGENT_LOOP_TICK_<purpose> {"prompt":"<prompt>"}'
done
```

1. 既存のターミナルに、既に稼働中の一致するループがないか確認する。
2. `notify_on_output` を付けてバックグラウンドのシェルループを 1 つ起動する。
3. 一意のセンチネルと、`^AGENT_LOOP_TICK_<purpose>` のような正規表現を使う。
4. 正常に起動したことを 1 回スモークチェックで確認する。
5. ループを仕掛けた直後にプロンプトを 1 回すぐに実行する。
6. 最初のセンチネルは最初の sleep の後にのみ届くはずなので、起動時にプロンプトが二重実行されることはない。
7. 求められたらループを停止できるよう PID を記録しておく。
8. 次の内容を簡潔に確認として伝える: 間隔、プロンプトを既に 1 回実行済みであること、最初の tick がいつ届くか、停止するまで各 tick でループが発火し続けること。以降の tick では、何が変わったかを短く報告する。停止時には、ループが停止したこととその理由を伝える。

## 動的スケジュール

ユーザーはエージェントに自らペース配分してほしい場合です。次の反復を実行する価値を何が生むか — 時間の経過か、観測可能なイベントか — を判断してください。

1. **プロンプトをいますぐ実行する。**
2. **次の実行がイベント（git の ref が進む、ログ行がマッチする、ファイルが変わる、CI チェックが完了する）に依存する場合**、そのイベント発火時にのみセンチネルを出力するバックグラウンドの監視プロセスを、`^AGENT_LOOP_WAKE_<purpose>` に対する `notify_on_output` 付きで仕掛ける。仕掛けるのは 1 回だけ。以降の tick でまだ動いていればスキップする。
3. **ターンの最後に、時間ベースのワンショット起床を仕掛ける**:

```bash
sleep <seconds>
echo 'AGENT_LOOP_WAKE_<purpose> {"prompt":"<prompt>"}'
```

   監視プロセスが仕掛けてあるなら、これは **フォールバックのハートビート** — アイドル tick が純粋なオーバーヘッドにならないよう長めに設定する。監視プロセスがないなら、これがペースそのもの — 結果を再確認する価値が出るタイミングに基づいて遅延を選ぶ。

4. **起床時**、最新のペイロードを読み、その `prompt` を実行し、次のハートビートを再度仕掛ける（監視プロセスは終了していた場合のみ再度仕掛ける）。出力による起床と完了通知の両方が届いた場合は、出力に対して行動し、完了通知は無視する。
5. **停止するには**、監視プロセスの PID を kill し、次のハートビートを仕掛けない。
6. 次の内容を簡潔に確認として伝える: 自己ペース配分していること、監視プロセスが主要な起床シグナルかどうか、選んだフォールバック遅延、プロンプトを既に実行済みであること。

## プロンプトペイロード

起床通知には、送信されたプロンプトではなく出力ファイルのパスが含まれます。プロンプトはセンチネルの隣に、できれば JSON として置いてください。起床時には、一致する最新の行を読み、その `prompt` に基づいて行動します。プロンプトは tick ごとに異なってもかまいません。

## 指針

- シェルコマンドのタイトルは `Loop <schedule>: <prompt>` とする（例: `Loop every 5m: check deploy status`）。
- ループの構文はユーザーのシェルに合わせる（例: Windows では PowerShell の `while ($true) { ... Start-Sleep }`）。上記の例は bash。
- エージェントが起床通知を必要とする場合は、OS の cron より監視付きシェル出力を優先する。stdout が監視対象タスクに接続されたままになる。
- 無関係な出力が通知を発火させないよう、ループごとに一意のセンチネルを使う。
- ループ内でノイズの多いコマンドを避ける。
- 固定ループや動的スリーパーを重複して作らない。
- ユーザーが停止を求めたら、記録しておいたループ / スリーパーの PID を kill し、その後シェルタスクを await して、完了通知が消費され後からエージェントを起こさないようにする。別の動的起床をスケジュールしない。
