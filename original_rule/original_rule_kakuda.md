# 1. 開発上の制約

- 作業後はリンターを確認し、エラーがあれば解消する。
- 人間の特定フレーズは §2 に従う。
- 新規実装は `docs/architecture/architecture.md` の技術スタックに従い、その公式ドキュメントを確認してから書く。未記載、または記載と違う実装をする場合は、使う側の章（§5 または §6）だけを適用する。
- コードの書き方は §4。React / TypeScript なら §5、Python なら §6 も適用する。
- スキルは §7。リポジトリ内にスキルを置かない。


# 2. ユーザーから特定の指示がある場合の対応

## 「整理して」

着手前に `src/` をすべて確認し、実装状況を `docs/agent_docs/YYYYMMDD_HHMM_プロジェクト実装状況.md` に記録する。冗長・役割重複・バグになりそうな実装は、DRY で最も単純な形に直す。

## 「UI を見直して」「デザインを確認して」

`web-design-guidelines` を適用して対象を監査する。直すのは §4 の「使いやすさの下限」に関わる指摘だけ。見た目のインパクトを削る指摘は、理由を添えて人間に確認してからにする。

## 「バグを直して」「動かない」

`systematic-debugging` を適用し、根本原因を特定してから直す。症状を隠す修正（条件分岐での回避、フォールバック）は禁止。


# 3. 公式ドキュメント

- 新たに書く箇所は、採用フレームワークの最新公式ドキュメントを確認してから書く。
- 技術スタックの正は `docs/architecture/architecture.md`。
- スキルと公式ドキュメントが食い違うときは公式ドキュメントを優先する。


# 4. 共通プログラミング原則

## 思考と計画

コードを変える前の作業開始宣言（何を・どのファイルで・どこまでを 2〜3 行）で、次を簡潔に述べる。
1. 現状の課題・仕様
2. ゴール
3. 変更箇所の最小化
4. 実装手順

例外・エッジケースは自分で検証する。テストコードは書かず、アプリを起動し Cursor 内蔵ブラウザで操作・スクリーンショットして確認する。セルフレビューを短く述べてから完了する。

## コード品質と設計

- 最もシンプルで読めるコードにする。過度な抽象化はしない。重複は DRY で一つにまとめる。
- エラーを飲み込まない。フォールバックで別の値を返さない。エラー情報をすべて出して処理を停止する。
- UI は目を引くことを最優先する。配置・余白・レスポンシブなど使いやすさの下限は守る。目を引くための奇抜さは禁止しない。
  - 新しい画面・大きな UI 変更は `frontend-design` に従い、テンプレートに見える UI を作らない。
  - 使いやすさの下限は `web-design-guidelines` で判定する。


# 5. React / TypeScript を使う場合

使わない場合、この章は適用しない。

- コンポーネントは `export const ComponentName = () => {}`。1 コンポーネントは 1 関心事。巨大なら子や Hook に分ける。最初から細かく分けすぎない。
- boolean props が 3 つ以上になったら `vercel-composition-patterns` で合成し直す。
- `any` 禁止。不明なら `unknown` と型ガード。Props・引数・戻り値には `interface` または `type` を明示する。
- データ取得・レンダリング・バンドルは `vercel-react-best-practices` に従う（直列 await、不要な重いクライアント import、無駄な再レンダリングを避ける）。
- 本章（`export const`、`any` 禁止、型の明示）とスキルが食い違うときは本章を優先する。


# 6. Python を使う場合

使わない場合、この章は適用しない。

- PEP 8。インデントはスペース 4。関数・変数は `snake_case`、クラスは `PascalCase`。引数と戻り値に型ヒントを付ける。

  ```python
  def get_user_data(user_id: str) -> dict:
  ```

- 巨大な単一スクリプトにしない。機能ごとにモジュールへ分ける。最初から細かく分けすぎない。
- 依存の追加・変更は独断でせず、ライブラリ名と理由を人間に伝える。


# 7. スキル

導入済み。本体は `~/.agents/skills/<name>/SKILL.md`。該当作業の着手前にそのファイルを読む。リポジトリ内の `.agents/skills/` / `.cursor/skills/` にも、ホームのスキルディレクトリにも、追加・削除・編集しない。新しいスキルが必要なら名前と理由を人間に伝える。

| 場面 | 読むスキル |
| --- | --- |
| 実装前に仕様の穴を潰す（人間が grill を指示したとき） | `grill-me`（実体は `grilling`）。質問は 5 分・10 問以内。決まったことは人間が `concept.md` に書く |
| 新しい画面・大きな UI | `frontend-design` |
| React のコンポーネント・データ取得 | `vercel-react-best-practices` / `vercel-composition-patterns` |
| 「UI を見直して」 | `web-design-guidelines` |
| 「バグを直して」「動かない」 | `systematic-debugging` |
| 実装のたびの動作確認 | スキルではなく Cursor 内蔵ブラウザ |

スキルの手順より `agent_rule.md` と本ファイルが優先する。次は実行しない。
- git 操作
- テストコードの作成（アプリ起動で代替）
- ポインタファイルや `docs/` へのスキル独自ファイル（`CONTEXT.md`、`docs/adr/` 等）
- 依存のインストール

使ったスキル名は、作業メモの「やったこと」に 1 行で書く。
