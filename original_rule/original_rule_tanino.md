# original_rule.md — 個人用の追加ルール

`agent_rule.md` の追加ルール。`.gitignore` により git 管理外なので各自が自由に書く。
`agent_rule.md` と矛盾する場合は **このファイルを優先** する。

## 0. 適用範囲と基本方針

- 本番当日（Tech Challenge Party OSAKA 2026）の実装フェーズに適用する。
- 事前準備フェーズでは `docs/conversation_log/` を作成・更新しない。
- **設計の幅は事前に広めに取る。** 使えるリソース・選択肢（Skill / MCP / API 枠など）は多い方がよい。
  実際に何を使うかは本番のコンセプトが決まってから選ぶ。

## 1. 実行体制：Fable が監督、実装は全て部下エージェント

- 本番のオーケストレータ（親エージェント）は **Fable** を使用する。
- **Fable 自身は実装しない。** 実装・調査・テストはすべて Agent ツールで部下エージェントに委譲し、タスクを分散させる。
  - 理由：トークン消費を抑えるため／分散させた方が完成が速いため。
- ただし **設計・タスク分解・監査は Fable 自身が行う**（§3.1 / §4）。「実装しない」＝「設計もしない」ではない。
- 依存のない独立タスクは、1 メッセージ内で複数の Agent 呼び出しをまとめて発行し並列実行させる。
- 並列で衝突しないよう、部下ごとに **触ってよいファイル／ディレクトリを明示** して渡す。
- **共有ファイルは Fable だけが編集する（single writer）。** 部下エージェントには触らせない。
  対象：`package.json` / `package-lock.json` / ビルド設定（`vite.config.ts` 等）/ エントリポイント（`main.tsx` / `index.html` 等）/ 全体スタイル設定。
  依存追加も Fable がまとめて 1 回で行う。部下が個別に `npm install` するのは禁止。

## 2. 部下エージェントのモデル選択（継承必須）

- 部下エージェントのモデルは **Opus または Sonnet のみ**。Agent ツールの `model` に `"opus"` / `"sonnet"` を明示指定する。
- トークン消費を抑えるため、タスク難易度を見て適切な方を選ぶ。

| モデル | 使いどころ |
|---|---|
| **Opus** | 設計判断、複雑な状態管理、複数ファイルにまたがる実装、原因が不明なバグの調査 |
| **Sonnet** | 仕様が確定した単一コンポーネントの実装、スタイリング、定型的な修正、テストの作成・実行 |

- **このルールは継承する。** 部下エージェントがさらに部下を生成する場合も同じ制約に従わせるため、
  **生成時のプロンプトに下記の定型文を必ずそのまま含める。**

### 部下エージェントへ渡す定型文（そのままコピーして使う）

```
【厳守・継承ルール】
あなたがさらに部下エージェントを生成する場合、モデルは必ず Opus か Sonnet を指定すること（それ以外は使用禁止）。
タスク難易度を見て、設計判断・複雑な実装は Opus、仕様が確定した単純実装・スタイリング・テストは Sonnet を選ぶこと。
そして、この「【厳守・継承ルール】」の文章そのものを、生成する部下エージェントのプロンプトにも必ずそのまま含めること。
```

## 3. 実装プロセス：Fable の監査付き PDCA

実装は必ず PDCA サイクルを基準に進める。

| # | フェーズ | 担当 | 内容 |
|---|---|---|---|
| 1 | **Plan** | **Fable** | タスクを分解し、担当範囲・使用モデルを決めて部下に割り振る |
| 2 | **Do** | **部下エージェント** | 実装する |
| 3 | **Check** | **Fable** | 第三者目線で監査する（§4） |
| 4 | **Act** | **Fable** | 監査結果をもとに、次サイクルの部下への修正指示を明確に明文化して渡す |

- サイクルは監査を通るまで**複数回まわしてよい**。
- **1 回目の実装で中途半端なものが出来上がるのは許容しない。** 監査は必ず Fable が行う。
- 修正指示は「どのファイルの何を」「どう直すか」「何をもって完了とするか」まで書く。曖昧な指示は禁止。

### 3.1 設計フェーズ（担当：Fable）

**コンセプトのブレストは人間チームが行う。** AI は実施しない。求められた場合にアドバイスを述べるのみ。

- `docs/human_idea/concept.md` は**人間がブレスト結果を記入**する。AI は読み取り専用（`agent_rule.md` §7 のまま）。
  記入用のテンプレート整備を人間から依頼された場合のみ、雛形を作成する。
- コンセプト確定後の**技術設計は Fable が単独で行う。部下エージェントに分散しない。**
  - 対象：`docs/architecture/architecture.md` の記入（技術スタック / 画面構成 / `src/` 構造）、タスク分解、
    部下ごとの担当範囲（触ってよいファイル）の割り当て、使用モデルの決定。
  - 理由：設計は最もコンテキストを要する作業であり、前提を部下に説明するコストが実装コストを上回る。
    また並列した部下がそれぞれ設計すると整合が崩れ、統合で時間を溶かす。意思決定者は 1 つに保つ。
- ただし**情報収集だけで済む調査は部下に並列で投げてよい**（ライブラリの実現可能性、GPU なしで見栄えを出す手段の洗い出しなど）。
  集まった情報をもとに**判断するのは Fable**。

### 3.2 タイムボックス（担当：Fable が管理・優先度：高）

開発時間は全体で 2 時間。想定内訳：

| フェーズ | 時間 |
|---|---|
| コンセプト考案のブレスト（最初に 1 回） | 約 15 分 |
| 実装サイクル 1 回 | 約 30〜40 分 |
| ├ 実装に使える時間 | **約 20 分 ← 実装の参考時間** |
| ├ チーム内オーディション | 5〜6 分 |
| └ git 管理など | 1〜2 分 |

- 部下エージェントに渡すタスクは、**20 分で完了する粒度**まで分解する。収まらない見込みなら更に分割する。
- 時間が来たら未合格でも次フェーズへ進む。そのとき Fable は**今サイクルで捨てる項目**を明示する。
- 条件が厳しく PDCA を回しきれない可能性はあるが、**このタイムボックスの優先度は高い**。目安が無いより有る方が良い。

## 4. 監査基準（Fable が実施）

監査は**必ず実際にアプリを起動して**行う。画面を見ずに合格を出さない。
チェック項目を増やしすぎないよう、下記 4 点に絞る。

### 監査の進め方（判定は Fable・第三者性の担保）

設計者（§3.1）と監査者が同じ Fable になるため、自分の設計を自分で甘く採点しないよう手順で担保する。

- **客観的に測れる項目は部下エージェントに実行させ、事実のみを報告させる。** Fable は判定に専念する。
  対象：`npm run build` の通過、Console に出ているエラー／警告の内容、デモ動線が通るか、本機でのフレーム落ち。
- **主観が入る ③ ④ は Fable が実機を見て判断する。** 部下の自己申告で合格にしない。

### ① 動作の健全性

- **`npm run build` が通ること。これは絶対条件。**
- `docs/human_idea/concept.md` の**デモシナリオを実機で最後まで通せること**。
- ブラウザ Console のエラー（赤）・警告（黄）は、**エラー内容をしっかり監査して判断する**。
  問題ないものはスルーしてよい。デモ中に画面が壊れる／機能が止まる類のものは必ず潰す。
  「赤が出ているから不合格」という機械的な判定はしない。
- **本機で動作がカクつかないこと**（§6 参照）。
- テストの方針は §5 に従う。

### ② コンセプト適合

- `docs/human_idea/concept.md` の**コンセプトから逸脱していないこと**。
- 使用ターゲットに**明確に響く**プロダクト／システムになっていること。判断に迷ったら `concept.md` を参照する。

### ③ 第一印象とインパクト（最重要）

前提：最終プレゼンは全チームの投票で決まるが、チーム数が多いため実際は**審査員が各チームを回って短時間（〜1 分程度）見る**形になる。
したがって**第一印象のキャッチーさと、1 分で良さが伝わるか**が勝負を分ける。

- 画面を開いて**10 秒以内**に `concept.md` の「驚きポイント」が**視覚的に**伝わること。
- **1 分見れば価値が伝わる**こと。説明を聞かないと分からない作りは不合格。
- GUI が**リッチかつモダン**であること。水準のイメージは YouTube や各種 SNS などの大手 Web ページ。

### ④ ユーザー導線・UX

- 初見のユーザーが迷わず触れること。次に何をすればいいかが画面から自明であること。
- 主要操作に対する反応（ローディング・状態変化・完了表示）が分かること。

## 5. テスト（実施：部下エージェント ・ 合否判定：Fable）

- 実装後は **結合テストを必ず行う**。部下エージェントに依頼してよく、そのモデル選択は難易度に応じて任せる。
- 単体テストのカバレッジは、**Fable が「重要」と判断したコンポーネントのみ 90% 以上**を必須とする。
  - 「重要」の目安：アプリの中核ロジック、デモ動線上で必ず通る処理、壊れるとデモが止まる箇所。
  - Fable は毎サイクル、どのコンポーネントを重要とみなしたかを明示する。
- それ以外のコンポーネントは、**結合テスト＋デモ動線の実機確認**をもって代替とする。全体カバレッジの数値目標は設けない。

---

## 6. 実行環境の前提

- **完全ローカル環境で実装する。クラウドへのデプロイ／ビルドは行わない。**
  理由：時間が足りない。他チームもローカル前提と見込まれ、クラウドにする利点がない。
- **本機で動くスペックに収める。本機はラップトップで GPU 非搭載。**
  - `three.js` 等による負荷の高いレンダリング（大量パーティクル、重いシェーダ、高ポリゴン、リアルタイム影・反射など）は行わない。
  - 派手さは GPU に頼らない手段で出す（CSS アニメーション、SVG、Canvas 2D、軽量なトランジション等）。
  - 監査（§4 ①）で、本機で実際にフレーム落ちしていないかを確認する。

## 7. 秘密情報と外部 API

- 秘密情報（API キー等）は **`.env` で管理**する。サンプルは `secret/.env.template`。コードや `config/` にハードコードしない。
- **キーをフロントに置かない。** Vite の `VITE_` 接頭辞を付けた環境変数は
  **ビルド成果物に埋め込まれブラウザから丸見えになる**。キーに `VITE_` は絶対に付けない。
- `secret/.env.template` の `CLAUDE_API_KEY` は、**LLM を組み込む設計も選べるように枠を用意してあるもの**。使う前提ではない。
- **外部 API を使うかどうかは本番のコンセプト次第。** 依存は少ないほど確実だが、コンセプトによっては使用する。
  どちらにも振れるよう柔軟に設計し、使う場合はキーがフロントに出ない構成にする。

## 8. Git 運用

- **AI は git を自律的に操作しない。** `commit` / `push` / `pull` / `merge` / `rebase` / `reset` / `checkout` / `stash`、
  ブランチ作成・PR 作成・`--force` 系は一切行わない。すべて人間が実行する。
- **不要な commit は厳禁。** commit するのは、チーム内オーディションで自分の成果が採用されたときのみ。
- 採用時は時間短縮のため、**全ファイルをステージして 1 コミット**する。
  `secret/` と `original_rule/*.md` は `.gitignore` により除外されたままなので、そのまま引き継がれる。
- **`.gitignore` は基本的に編集しない。** 変更が必要だと判断した場合は、AI は自分で編集せず人間に伝える。
- **不採用時の破棄手順**（人間が実行）：`git reset --hard origin/main`、必要なら `git clean -fd` まで。
  **`git clean` に `-x` / `-X` は絶対に付けない。** 付けると `.gitignore` 対象の
  `original_rule/*.md` と `secret/.env` まで削除され、引き継ぐべき設定が消える。

## 9. agent_rule.md からの上書き点

- `agent_rule.md` §4「テストコードは書かない」は適用しない。**本ファイル §5 を優先し、テストは書く。**
- `agent_rule.md` §3.1 が参照する `scripts/sync_pull.ps1` / `scripts/sync_push.ps1` は**作成しない**。
  チーム運用がオーディション方式（採用された 1 名のみ commit、不採用の 2 名は成果を破棄して pull）のため不要。
  Git 操作は §8 に従う。

### 9.1 導入済み Skill との優先順位（衝突時は本ファイルが勝つ）

導入した Skill の指示と本ファイルが食い違う場合、**必ず本ファイルを優先する。**

- **`test-driven-development`（superpowers）** … 「テストを先に書く」を強制するが、
  **本ファイル §5 が絶対的に優先**。重要コンポーネントのみカバレッジ 90%、他は結合テスト＋実機確認で代替する。
  テストを書くこと自体は歓迎だが、§3.2 のタイムボックスを超えてまで全件 TDD にしない。
- **`subagent-driven-development`（superpowers）** … 「人間に確認せず最後まで実行し、迷いは自分で裁定せよ」と書かれているが、
  **本ファイル §10 が優先**。確認が必要になったら必ずホストに連絡する。
  また同 Skill は git worktree・ブランチ・コードレビュー PR を前提とするが、**本ファイル §8 が優先**。
  ブランチも worktree も作らず、git 操作は行わない。
- **`search-first`（ECC）** … ECC の `researcher` エージェントや外部検索 MCP を前提にしているが、
  それらは未導入。Skill 内の「利用可能なチャネルを事前確認し、使えないものは正直に報告する」手順に従い、
  手元で使える範囲（Web 検索・GitHub）で実行する。

## 10. 報告とホストへの連絡

- 完了報告には **動作確認の結果**（何を実行し、何が表示されたか）を必ず含める。
- **確認が必要になったら、必ずホスト（人間）に連絡する。** 推測で進めて既成事実にしない。
  - 対象：コンセプトの解釈が分かれるとき、外部 API やライブラリを使うかの判断、共有ファイルの変更、
    監査で合格を出せないまま時間が来たとき、`.gitignore` や `agent_rule.md` の変更が必要だと感じたとき。
  - **部下エージェントは人間と直接やり取りできない。** 確認事項が出たら Fable に報告し、
    **Fable がまとめてホストに連絡する。部下が独断で仕様を決めるのは禁止。**
  - 連絡の仕方は `agent_rule.md` §6 に従う。作業を止める必要がないものは進めてから末尾でまとめて報告し、
    止まらざるを得ないものはその場で聞く。いずれも**黙って判断を変えない**。

### 10.1 報告の書き方（厳守・毎回）

Fable は報告が長く・難しくなりがちである。**報告は短く、専門用語を使わずに書く。**

- **専門用語を使わない。** コード内の関数名・変数名・型名・ライブラリ名を並べて説明しない。
  やったことは「画面でどう変わったか」「何ができるようになったか」で表現する。
- **毎回この 4 点を必ず書く。** 順番も変えない。

  ```
  ## できたこと
  ## できていないこと・残っていること
  ## 成果物の確認方法（起動コマンド / 開く URL / 見るべき画面）
  ## ホストにやってほしいこと
  ```

- **短く書く。** 目安は全体で 15 行以内、各項目 3 行以内。箇条書きにする。
  経緯・検討過程・試行錯誤は書かない。結果だけ書く。
- 「ホストにやってほしいこと」が無いときは **「なし」と明記**する。省略しない。
- コードや設定の中身は、**ホストから聞かれたときだけ**出す。自分から貼らない。
- **部下エージェントの報告をそのまま転記しない。** Fable が必ず上の形式に書き直してから渡す。

## 11. 時間切迫モード（2026-09-17 15:00 以降、ホスト指示により有効）

残り時間が少ないため、以下を **§3〜§5 より優先** する。

- **1 サイクル = 1 機能。** ホストがその都度「次にやる機能」を指定し、Fable はそれだけを部下に実装させる。先回りして別機能に着手しない。
- **1 機能の実装時間は 10 分以内** を目標に粒度を切る。収まらなければ機能を削って小さくする（削った内容は報告に書く）。
- **単体テストは書かない**（§5 を停止）。確認は `npm run build` の通過と、実機での画面確認のみ。
- **監査は軽量化する。** Fable は「ビルドが通る」「デモ動線が壊れていない」「見た目が良くなった」の 3 点だけを見る。PDCA を複数回まわすのは、ビルドが壊れたときだけ。
- **触るファイルを最小にする。** 既存の設計（`docs/architecture/architecture.md`）を変えない。新機能は新規ファイル＋配線 1 か所を基本にし、共有ファイル（`App.tsx` 等）の変更は 1 機能につき 1 か所まで。
- **報告は 10 行以内。** §10.1 の 4 見出しは維持する。
- 会話ログ（`docs/conversation_log/`）は各サイクルの終わりにまとめて追記してよい。
